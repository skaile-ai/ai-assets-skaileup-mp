1 The answerright pieces, wrong order

The collection has the right skills in the wrong order. The domain vocabulary gets its final form last (F08, F30), and the data model comes after every feature and screen (F17). In 3 of 4 flows, a hard gate has no upstream node that satisfies it (F01, F02, F03), and check.py does not look (F04). The editor cannot tell a finished node from the files, because no skill declares what it produces (F05). The reasons behind artifacts and the approvals stay in chat (F13, F23). The review holds 44 findings: 3 critical, 13 high, 21 medium, 7 low.

What is already right:

  • The skills are flat: 30 skills in one directory level, and the longest (ops-review) has 111 lines.
  • One artifact tree holds all 14 targets, from brief.md to 11_build/, so every skill writes to a known place.
  • scripts/check.py is the single gate of the collection; its flow rule has one gap (F04).
  • The glossary format keeps an _Avoid_ list per term, so a rejected word has a home.
  • A decision enters decisions.md only after the three-test check.
  • Feature dossiers are frozen records of the reasons (08_dossiers/).

7 Target shapeone hierarchy, one owner per artifact

The principle: one hierarchy (domain language, data model, features, screens), one owner per artifact, and every decision of the user lands in a markdown file that the editor opens (F08, F17, F13).

Proposed order of the standard flow:

  1. concept-scope and concept-onboard: answers.json is the one record of every answer (F06, F16).
  2. concept-brief: brief.md and goals.md. concept-reverse writes findings only (F09).
  3. Domain language (new): _concept/glossary.md, first level, one writer. Every later skill reads it first (F08, F30).
  4. concept-research runs alongside, before brand and journeys (F12).
  5. experience-journeys: stories use glossary terms and carry no candidate_entities (F18).
  6. Data model: architecture-datamodel moves ahead of the features (10_blueprint/datamodel/, conceptually 05_datamodel/). It names entities from the glossary only, and feature-map.json goes (F17, F33).
  7. spec-featuresets and experience-behaviors read the entities and never coin names (F18, F19).
  8. architecture-techstack and architecture-system run before any renderer (F02, F32).
  9. Feature loop with spec-feature: spec and screens. The dossier opens at step 2 (F23).
  10. experience-shell runs after the loop. Navigation comes from real screens (F25).
  11. mockup-walkthrough is the one mockup renderer, then mockup-annotate and mockup-feedback (F26).
  12. Build: build-scaffold, build-database, build-plan, build-implement.
  13. Quality: quality-test, quality-e2e, quality-review.
  14. ops-review and quality-release. trace.yaml is the single trace (F36).
