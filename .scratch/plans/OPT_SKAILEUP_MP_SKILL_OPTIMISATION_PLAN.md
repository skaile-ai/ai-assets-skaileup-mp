### Decisions

- **D1. Adopt Pocock's invocation convention for the five external skills; keep them global (no vendoring).** Premise 6 of the migration map rules vendoring out, and `tdd`/`code-review` are maintained upstream with references we would have to track. Phrasing becomes uniform (`Call the Skill tool with "tdd"`), `triage` is phrased as an instruction to the human because it is user-invoked, and each call states hard or soft per Pocock ADR 0001: **hard** = `tdd`, `code-review` (build-implement, quality-review say the skill "calls rather than restates" them — nothing in the body can stand in); **soft** = `grilling` (spec-feature step 2 already lists the ground the interview has to cover, so the skill can run the rounds itself), `diagnosing-bugs` (quality-review can hand the failure back to the user instead), `triage` (skaileup can skip intake judgement and say so). *Rejected:* vendoring copies under `skills/` — breaks premise 6 and the nine-domain naming (`tdd` has no domain segment); a `requires:` entry in frontmatter — ADR 0011 allows only machine-read keys, and no host reads a global-skill dependency.
- **D2. Encode D1 as a `check.py` rule, not as prose only** (pstack `principle-encode-lessons-in-structure`; the collection's own ethos per `CLAUDE.md:30`). The external-skill list lives once, as a constant in `check.py`, and the rule fires on an unknown name in a Skill-tool call and on a bare `/name` for any model-invoked or collection skill. Both are **house** rules (`rep.house`, F5a): the collection chose the phrasing; no host breaks without it. *Rejected:* a rule that every backticked external-skill mention sits inside a "Call the Skill tool" sentence — too brittle (prose legitimately *mentions* `tdd` when describing a boundary, e.g. `quality-test:21`).
- **D3. Rewrite `contracts/agent_patterns.md` into the house shape and prune what has no reader or no referent** (ADR 0003/0008 style; ADR 0004 "contracts earn their place"). Kept section names stay identical where a skill cites them (`Questions Are Standalone Messages`, `Subagent Dispatch`, `Next-Step Suggestion`), so no skill citation moves. Three patterns are added from the libraries (D4–D6). *Rejected:* deleting the file (7 readers, and the template names it as the home for standalone/next-step behaviour); restyling only, keeping dead patterns — leaves `verbosity`, `modes.research`, `orchestrator` and `prog-expert` text that describe a host that does not exist.
- **D4. Adopt pstack's "steps become the todo list verbatim"** (poteto-mode Playbooks section) as an agent pattern, because the host runs one skill per node and the agent otherwise re-sequences a 7–12-step body from memory; the pattern costs one paragraph and no frontmatter. *Rejected:* pstack's sticky router/playbook layer — the flow graph is this collection's playbook (ADR 0010: order lives in the graph), and `skaileup` is deliberately a one-answer router (`skills/skaileup/SKILL.md:12-19`).
- **D5. Adopt pstack's evidence label ("measured, inferred, or guess, in the same sentence"; "never hand the human a check you could run") in two places only:** `contracts/evaluator.md § Stance` (three verdict-writing readers) and the agent-patterns reply guidance for the Completion Summary. `concept-reverse` already has it (F6). *Rejected:* a principle skill — see D7.
- **D6. Add a design-red-flags screen to `architecture-system` step 4 as a `references/` file** (single reader → `references/`, not a contract, per `docs/skill-template.md:49-53` and ADR 0004). Content: the four Ousterhout red flags both libraries use, phrased as the question to ask of each custom module / protocol / integration before it is written down, plus Pocock's "design it twice" as a one-line rule for any module with more than one plausible interface. *Rejected:* pstack's multi-model `arena` — model fan-out is a harness capability this collection does not assume; `build-plan` is not touched because its seams come from the feature spec and the screen files, not from an interface design.
- **D7. No principles layer.** pstack's 24 `principle-*` skills are engineering rules for the build side; this collection delegates build discipline to `tdd`/`code-review` (D1) and its own rules are already encoded as contracts (`golden_principles.md`) and as `check.py`. Twenty-four extra skill directories would also break the `domain-skill` naming invariant (`CLAUDE.md:15`) and the nine domains (ADR 0002). *Kept from the idea:* the "name the rule that shaped the decision" mechanic is already the collection's **decision record** three-test (`CONTEXT.md:145-150`); nothing to add.
- **D8. Add a README skill index and make `check_docs` require it to be complete** (pstack README table; Pocock bucket READMEs). Fixes F8 at the same time. *Rejected:* generating the README from frontmatter — a generator is a second source for a 30-row table whose only reader is a human; the check keeps the hand-written table honest in both directions.
- **D9. Not adopted, logged for the review:** Pocock plugin manifest / changesets (this collection ships via `skaile.yaml` to its own hosts, F9: no version consumer); Pocock `handoff.md` session states (ADR 0005 warm/cold boundaries and the `STATUS:` block already cover it); pstack `unslop` (no evidence stakeholder artifacts are sloppy; would need ≥2 step-readers to earn a contract); pstack `reflect`/Pocock `retro` learning loop (improves the collection from transcripts — a separate effort on the repo's own workflow, not a skill change); pstack "never block on the human" (conflicts with the concept side, where approval steps are the product: `architecture-system:69-72`, `build-plan:67-71`); pstack `create-verification-skill` (`quality-e2e`/`quality-release` already drive the real app per flow); rewriting `evaluator.md § Laws` out of MUST form (restyle without a behaviour change — out of scope here; one line in D5 notes it for a later ticket).
- **D10. Record D1–D9 as `docs/adr/0012`.** They are hard to reverse (a phrasing rule enforced by CI), surprising without context (why no principles layer, why the dependency on five foreign skills is deliberate), and a real trade-off — the three-test in `CONTEXT.md:145-150`.
- **D11. Review pass (second read against the code) — five corrections, one addition.** (a) `rule=` on `rep.error` raises without `fact=` (F5a) → the new rules are `rep.house`, fixtures assert on message text. (b) `SKILL_TOOL_CALL_RE` was case-sensitive while three of the six rewritten calls are mid-sentence lower-case → `[Cc]all`. (c) README links as `./skills/name/` are invisible to `SKILL_PATH_RE` (F11) → `skills/name/`, and the completeness rule reuses `SKILL_PATH_RE` so both directions read the same tokens. (d) The S3 draft mapped *guess* to severity `low`, inventing a label→level mapping the `§ Flag shape` table does not have and contradicting "a nit worth recording once" → a guess is not a finding; the agent runs the check or omits the claim. (e) `quality-review:40` draft said "where the project has a local test path" — an invented condition → plain soft fallback. (f) **Added** S2.12: a `§ <Section>` citation check (F10) — S2 renames and promotes headings in a file five skills cite by section, and nothing would catch a dangling `§`; it is the same encode-in-structure move as D2 and lands green. *Considered, not added:* a `check.py` rule that every skill description carries `Triggers on` (F2: four `mockup-*` skills would fail today; a rule that starts red on unrelated files is a separate ticket).

### S3 — Evidence label in `contracts/evaluator.md` (D5)

Append to `## Stance` (`:9-16`): "Every finding states how it was obtained in the same sentence — **measured** (seen in the artifact or the running app, quoted or reproduced) or **inferred** (follows from something measured, and names it). A claim that is neither is not a finding: run the check that would make it one, or leave it out — never hand the user a check you could run.
